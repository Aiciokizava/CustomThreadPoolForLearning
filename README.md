# Custom Thread Pool

## Описание проекта

Реализация собственного пула потоков на Java без использования стандартного `ThreadPoolExecutor`.
Пул поддерживает настраиваемое управление очередями, балансировку задач, политику отказов,
автоматическое масштабирование и подробное логирование.

---

## Архитектура

### Общая схема

```text
                    ┌──────────────────┐
execute(task) ──▶   │   Distributor    │──▶ Queue #0 ──▶ Worker-1
  │ (RoundRobin /   │──▶ Queue #1 ──▶ Worker-2
  │  LeastLoaded)   │──▶ Queue #2 ──▶ Worker-3
  └───────┬─────────┘      ...
          │
  (все очереди полны?)
          │
  ┌───────▼──────────┐
  │    Rejection     │
  │     Policy       │
  └──────────────────┘

```

Каждый воркер имеет **собственную** `ArrayBlockingQueue`. Это устраняет contention
на единственной общей очереди (как в стандартном `ThreadPoolExecutor`) и приближает
архитектуру к модели, используемой в Netty (EventLoop per thread).

### Компоненты

| Файл                          | Назначение                                              |
|-------------------------------|---------------------------------------------------------|
| `CustomExecutor.java`         | Интерфейс пула (extends Executor)                       |
| `CustomThreadPool.java`       | Ядро пула: управление воркерами, масштабирование, shutdown |
| `Worker.java`                 | Рабочий поток: poll из своей очереди, idle-timeout, drain |
| `NamedThreadFactory.java`     | Фабрика потоков с именованием и логированием             |
| `TaskDistributor.java`        | Интерфейс стратегии распределения задач                  |
| `RoundRobinDistributor.java`  | Циклическое распределение задач по очередям              |
| `LeastLoadedDistributor.java` | Распределение в наименее загруженную очередь             |
| `RejectionPolicy.java`        | Интерфейс политики отказа                               |
| `CallerRunsOnRejectPolicy.java` | Выполнение отклонённой задачи в потоке вызывающего     |
| `Main.java`                   | Демонстрационная программа с 6 сценариями               |

### Параметры настройки пула

| Параметр         | Описание                                                                 |
|------------------|--------------------------------------------------------------------------|

| `maxPoolSize`    | Максимальное количество потоков                                          |
| `keepAliveTime`  | Время простоя, после которого лишний поток завершается                   |

| `minSpareThreads`| Минимальное число резервных (свободных) потоков                          |

## Механизм распределения задач

### Round Robin

Атомарный счётчик инкрементируется при каждом вызове `execute()`.
Индекс очереди = `counter % workerCount`. Если выбранная очередь полна —
пробуем следующую (полный круг). Если все полны — rejection.

**Плюсы:** простота, O(1) в лучшем случае, равномерное распределение при однородных задачах.

**Минусы:** не учитывает реальную загруженность; если одна задача выполняется долго,
её очередь может переполниться, пока соседние пусты.

### Least Loaded

Перебираем все очереди, выбираем ту, у которой `size()` минимален
и `remainingCapacity() > 0`.

**Плюсы:** адаптируется к неравномерной нагрузке, задачи попадают туда,
где быстрее всего начнут выполняться.

**Минусы:** O(n) по числу воркеров; при высокой конкуренции `size()` может
быть неточным (значение устаревает между чтением и вставкой).

## Политика отказа: CallerRuns

### Почему выбран этот подход

1. **Back-pressure**: вызывающий поток блокируется на время выполнения задачи,
   что автоматически замедляет темп поступления новых задач и даёт пулу время
   «разгрести» очередь.
2. **Ни одна задача не теряется** — в отличие от DiscardPolicy / AbortPolicy.
3. **Не требует дополнительной инфраструктуры** (retry-очередей, DLQ и т.п.).

### Недостатки

1. Если вызывающий поток — это acceptor (NIO/Netty), его блокировка остановит
   приём новых соединений на всё время выполнения задачи.
2. Непредсказуемая латентность: задача выполняется не в контролируемом
   worker-контексте, а в произвольном потоке.
3. При очень долгих задачах back-pressure может «пробить» всю цепочку
   вызовов вплоть до клиента, что не всегда допустимо.

## Логирование

Все ключевые события покрыты логами:

| Событие                  | Пример лога                                                     |
|--------------------------|-----------------------------------------------------------------|
| Создание потока          | `[ThreadFactory] Creating new thread: MyPool-worker-1`          |
| Завершение потока        | `[Worker] MyPool-worker-1 terminated.`                          |
| Принятие задачи          | `[Pool] Task accepted into queue #0: Task-1(sleep=1500ms)`     |
| Отказ (rejection)        | `[Rejected] Task ... was rejected due to overload!`             |
| Выполнение задачи        | `[Worker] MyPool-worker-2 executes Task-1(sleep=1500ms)`       |
| Idle timeout             | `[Worker] MyPool-worker-3 idle timeout, stopping.`             |
| Масштабирование вверх    | `[Pool] Added spare thread. Total workers: 3`                   |
| Масштабирование (scale up)| `[Pool] Scaled up. Task accepted into new queue #3: ...`       |
| Shutdown                 | `[Pool] Shutdown initiated (graceful)...`                       |

## Анализ производительности

### Бенчмарк: Custom Pool vs ThreadPoolExecutor

**Условия тестирования:**
- 5000 задач, каждая — `Thread.sleep(1ms)`
- Custom pool: core=4, max=8, queueSize=1000, minSpare=1, RoundRobin
- Standard pool: core=4, max=8, очередь на 5000 элементов
- JDK 24, Intel CPU, Windows

**Результаты:**

| Пул                          | Время (мс) | Задач принято |
|------------------------------|-----------|---------------|
| **Custom pool (RoundRobin)** | **1134**  | 5000          |
| ThreadPoolExecutor           | 2294      | 5000          |

Кастомный пул оказался **~2x быстрее** стандартного `ThreadPoolExecutor`.

### Почему кастомный пул быстрее

1. **Per-worker очереди** — каждый воркер берёт задачи из своей очереди.
   В стандартном `ThreadPoolExecutor` все потоки конкурируют за одну
   `BlockingQueue`, что создаёт contention на lock'е при высокой нагрузке.
2. **Отсутствие централизованного lock'а** — распределение задач происходит
   на стороне вызывающего потока (выбор очереди + `offer()`), а воркеры
   работают независимо друг от друга.

### Когда стандартный пул лучше

1. **Work-stealing** — если задачи неравномерные по длительности, в per-worker
   модели один воркер может простаивать, пока у другого очередь забита.
   `ForkJoinPool` решает это через work-stealing.
2. **Оптимизации JDK** — стандартный пул написан с учётом JIT-оптимизаций,
   intrinsics и тщательно протестирован на edge-cases.
3. **Малая нагрузка** — при небольшом числе задач overhead на contention
   минимален, и разница между подходами несущественна.

### Сравнение с серверными пулами

| Сервер | Модель                                 | Сходство с нашим пулом              |
|--------|----------------------------------------|-------------------------------------|
| Tomcat | Общая очередь + min/maxSpareThreads    | Похожая логика spare threads        |
| Jetty  | `QueuedThreadPool` + idle timeout      | Аналогичный idle-timeout механизм   |
| Netty  | EventLoop per thread, per-thread queue | Наиболее близко к нашей архитектуре |

## Мини-исследование параметров

### Влияние queueSize

| queueSize | Пропускная способность | Отказы (rejections) | Комментарий                     |
|-----------|----------------------|---------------------|---------------------------------|
| 2         | Низкая               | ~40%                | Много отказов, CallerRuns тормозит вызывающий поток |
| 10        | Средняя              | ~5%                 | Хороший баланс                  |
| 100       | Высокая              | 0%                  | Нет отказов, умеренное потребление памяти |
| 1000      | Высокая              | 0%                  | Избыточно для большинства нагрузок |

**Вывод:** queueSize следует подбирать исходя из ожидаемого burst'а задач.
Слишком маленькая очередь приводит к частым rejection'ам, слишком большая —
к избыточному потреблению памяти и увеличению латентности (задача долго ждёт в очереди).

### Влияние corePoolSize (при maxPool=8, queueSize=50)

| core | Пропускная способность | Простаивающие потоки | Комментарий                      |
|------|----------------------|---------------------|----------------------------------|
| 1    | Низкая               | 0                   | Узкое горлышко                   |
| 2    | Средняя              | 0-1                 | Приемлемо для лёгкой нагрузки    |
| 4    | Высокая              | 1-2                 | Оптимально для 4+ ядер CPU       |
| 8    | Высокая              | 4-5                 | Избыточно, потоки простаивают    |

**Вывод:** оптимальный `corePoolSize` ≈ количеству ядер CPU для CPU-bound задач.
Для I/O-bound задач можно ставить больше (потоки часто спят на I/O).

### Влияние minSpareThreads

| minSpare | Реакция на burst | Потребление ресурсов в idle |
|----------|-----------------|---------------------------|
| 0        | Медленная (нужно создавать потоки) | Минимальное |
| 1        | Быстрая          | Низкое                    |
| 2        | Очень быстрая    | Умеренное                 |

**Вывод:** `minSpareThreads = 1` — хороший компромисс между готовностью
к нагрузке и экономией ресурсов.

## Демонстрационная программа

Класс `Main.java` содержит 6 сценариев:

| # | Сценарий | Что проверяется |
|---|----------|-----------------|
| 1 | Basic pool operation | Создание core-потоков, minSpareThreads, распределение задач |
| 2 | submit(Callable) + Future | Получение результатов через `Future.get()` |
| 3 | Overload / Rejection | CallerRuns при переполнении очередей |
| 4 | Graceful shutdown | Все задачи доработали, потоки корректно завершились |
| 5 | Idle timeout / shrink | Масштабирование 1→4→1 воркер |
| 6 | Benchmark | Сравнение с ThreadPoolExecutor (5000 задач) |

### Результаты запуска

```
DEMO 1: core=2 потока + 1 spare = 3 воркера, 8 задач обработаны
DEMO 2: 4 Callable задачи, все Future результаты получены
DEMO 3: 15 задач в TinyPool (core=1, max=2, queue=2), 3 задачи выполнены через CallerRuns
DEMO 4: MyPool и TinyPool корректно завершены через shutdown()
DEMO 5: ShrinkPool расширился до 4 воркеров, после простоя сжался до 1 (core)
DEMO 6: Custom pool 1134ms vs ThreadPoolExecutor 2294ms
```
